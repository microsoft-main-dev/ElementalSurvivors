# План M7 — монетизация и полировка

Согласован с владельцем. Код пишется только после «ок» (правило 2 ТЗ).

## Решения владельца

1. **Вечных геймпассов нет вообще.** Вся монетизация — повторяемые покупки:
   временные бустеры (час / день / неделя), заряд «x10 награда за один забег»,
   пачки Prisms, VIP на 30 дней. Ни один товар не покупается «навсегда».
2. **Батлпасс отложен за MVP.** В M7 не входит; `purchases.battlePass` остаётся
   пустым полем схемы.
3. **VIP — дев-продукт на 30 дней**, а не пас. Поле `purchases.vipUntil` под это
   уже лежит в схеме с M3.
4. **Мобильная проверка — только эмуляция устройства в Studio.** Настоящего
   Android под рукой нет, поэтому второй критерий приёмки закрывается частично,
   и это записано явно, а не замазано.

## Что из этого следует

**Единственный вход денег в игру — `ProcessReceipt`.** Раз нет геймпассов, нет и
второго пути выдачи: ни `UserOwnsGamePassAsync`, ни проверки владения при входе.
Вся защита экономики от Robux сводится к одной функции — ровно как «забег
оплачивается один раз» сводится к `awardRun`. Это хорошая новость: критерий
приёмки проверяет то самое место, где может сломаться.

**Клиент в выдаче не участвует физически.** Покупка запускается клиентским
`MarketplaceService:PromptProductPurchase(player, productId)`, а дальше Roblox
разговаривает только с сервером. Подделать нечего — Remote в этой цепочке нет
вообще, и это единственная покупка в игре, которую не надо валидировать.

**`purchases.gamepasses` в схеме останется пустым навсегда.** Не удаляю (форма
профиля из раздела 6 ТЗ), но помечаю комментарием, чтобы через полгода никто не
искал, кто же его заполняет.

## Товары

Числа стартовые, лежат в конфиге, балансом не считаются (баланс заморожен до
конца MVP — правку цен владелец делает сам, когда захочет).

| Ключ | Вид | Что даёт |
|---|---|---|
| `Prisms80` … `Prisms1200` | `prisms` | 4 пачки донатной валюты. Нижняя не меньше 80 — цены призматического яйца |
| `BoostHour` / `BoostDay` / `BoostWeek` | `boost` | x2 Essence за забеги на 1 ч / 1 д / 7 д |
| `LuckyRun` | `charge` | x10 Essence за один засчитанный забег |
| `Vip30` | `vip` | 30 дней: x2 Essence, x2 потолок оффлайна, вторая прокрутка колеса |

Цену в Robux задаёт владелец в Creator Dashboard, в коде её нет — только числовой
`productId`. **Ноль в `productId` означает «продукт не заведён»**: лот рисуется
неактивным с пометкой, а не роняет панель. Так же устроен `Config/Branding`.

### Правила, которые надо решить до кода, и мои решения

- **Одинаковые бустеры продлевают срок, а не заменяют его.** Купить день поверх
  часа и потерять час — это возврат средств и жалоба.
- **Разные бустеры действуют одновременно, множители перемножаются.** VIP и
  недельный x2 вместе дают x4. Иначе покупка VIP «съедала» бы уже купленное.
- **Заряд `LuckyRun` списывается в `awardRun`**, вместе с выплатой, а не при
  входе на арену. Три пути выплаты уже сходятся туда — значит, и списание будет
  ровно одно, по тому же инварианту.
- **Заряд сгорает на любом засчитанном забеге, включая смерть.** Решение
  владельца: покупка страхует не результат, а попытку — не вышло, покупай заново.
  Длину забега при списании не проверяем, порога нет. На проигранном забеге
  множитель применяется к утешительным 10%, то есть выплата маленькая, и это
  задуманное поведение, а не потеря товара.
- **Множители трогают только Essence.** Опыт персонажа и таланты не ускоряются:
  иначе донат начинает давать силу, а раздел 10 ТЗ это прямо запрещает.
- **VIP хранится в `purchases.vipUntil`**, остальные бустеры — в
  `purchases.boosters`. Читает их один движок, `vipUntil` — не отдельная система,
  а запись с известным ключом; поле сохранено потому, что оно есть в ТЗ.

## Новые файлы

### `Shared/Config/Monetization.luau`
```lua
Monetization.Products: { ProductDef }
Monetization.ByKey: { [string]: ProductDef }
Monetization.ByProductId: { [number]: ProductDef }   -- пропускает нули
Monetization.Boosts: { [string]: BoostDef }
Monetization.IsConfigured(product: ProductDef) -> boolean
```
```lua
ProductDef = {
    key, kind: "prisms" | "boost" | "charge" | "vip",
    productId: number,          -- 0 = не заведён
    displayName, description,
    grant: { prisms: number?, boost: string?, seconds: number?, charge: string?, count: number? },
}
BoostDef = { key, displayName, essenceMult, offlineCapMult, wheelSpins, color }
```

### `Server/Services/PurchaseService.luau`
Единственный владелец `MarketplaceService.ProcessReceipt`. Больше никто в проекте
к `MarketplaceService` не обращается.
```lua
PurchaseService.SimulateReceipt(player, productKey, purchaseId) -> string  -- только Studio
PurchaseService.BuildView(player) -> StoreView
```
Порядок обработки чека — он же и есть критерий приёмки:
1. Профиль не загружен (игрок вышел, идёт загрузка) → `NotProcessedYet`.
   Ничего не выдаём: Roblox пришлёт этот чек снова, в том числе при следующем входе.
2. `purchaseId` уже в списке обработанных → `PurchaseGranted` **без повторной
   выдачи**. Это и есть защита от дубля.
3. Выдача через операции `DataService` → запись `purchaseId` → **синхронный сейв
   профиля** → только после успешного сейва `PurchaseGranted`.
4. Любая ошибка или падение сейва → `NotProcessedYet`. Игрок получит товар со
   следующей попытки Roblox; потерять деньги он не может.

Порядок «сначала сохранить, потом подтвердить» — единственный правильный:
подтвердить раньше сейва значит подарить товар вылету сервера.

### `Server/Services/BoostService.luau`
Активные бустеры: сроки, множители, заряды.
```lua
BoostService.GetMultipliers(player) -> { essence: number, offlineCap: number, wheelSpins: number }
BoostService.ConsumeRunCharge(player, runSeconds) -> number   -- 1 или множитель заряда
BoostService.BuildView(player) -> BoostsView
```
Истечение срока не требует таймеров: множитель считается от `os.time()` в момент
запроса. Просроченные записи чистятся при входе.

### `Shared/Config/Sounds.luau` + `Client/Controllers/SoundController.luau`
Звук в проекте отсутствует полностью. Конфиг устроен как `Branding`: **ноль =
звука нет, играет тишина**, поэтому код пишется и проходит приёмку до того, как
появятся ID.

Слоты, которые надо заполнить (список для владельца — см. «Ручные действия»):
попадание по врагу, смерть врага, подбор кристалла, левел-ап, выбор карточки,
получение урона, смерть игрока, выход босса, смерть босса, победа на уровне,
клик по кнопке, покупка, открытие яйца, прокрутка колеса, фоновая музыка лобби
и боя.

### `Client/UI/SettingsPanel.luau` + `Client/Controllers/SettingsController.luau`
Качество (авто / высокое / низкое), эффекты других игроков (все / рядом / выкл —
раздел 2.1 ТЗ), громкость звука и музыки, показ урона цифрами.

Хранение — **в профиле**: другой персистентности в Roblox нет. При первом входе
дефолт выбирается по устройству (`UserInputService.TouchEnabled` и размер
вьюпорта), дальше уважается выбор игрока.

### `Server/Services/TutorialService.luau` + `Client/Controllers/TutorialController.luau`
Обязательный первый вход (раздел 4 ТЗ): новичок не гуляет по лобби, а сразу
уходит в сюжетный уровень 1 с подсказками «двигайся», «кристаллы сами не
подберутся», «выбери карточку», затем возвращается и получает тур по лобби
(яйцо → питомец → портал). Флаг `flags.tutorial`, пропуска нет, повтора нет.
Сервер владеет флагом и фактом принудительного входа; клиент рисует подсказки.

## Как проверяется «ровно один раз» без Robux

Покупки не работают в Studio: окно оплаты там не открывается. Поэтому
`Balance.Debug.receiptTest` (ноль по умолчанию, **проверка на Studio стоит в
коде**, как у `offlineTestHours`): при значении «ключ продукта» сервер при входе
игрока прогоняет один и тот же `purchaseId` через настоящий `ProcessReceipt`
дважды и печатает в Output баланс до, после первого и после второго вызова.
Второй обязан не изменить ничего.

Это проверяет код. Реальную покупку владелец делает уже на опубликованном месте —
списание с самого себя проходит по-настоящему, и Robux в основном возвращается
как выручка разработчика, но не мгновенно.

## Ручные действия владельца (правило 11)

Расписываю по шагам отдельно, когда дойдём до шага 1. Коротко, что понадобится:
1. Создать 9 дев-продуктов в Creator Dashboard (Creations → место → Monetization
   → Developer Products), задать имя и цену в Robux, скопировать ID каждого.
2. Прислать мне 9 пар «ключ → ID» — я вписываю их в `Config/Monetization`.
3. Найти в Roblox Creator Store бесплатные звуки под список слотов и прислать ID.
   **Сам их выдумывать не буду** (правило 4): несуществующий Asset ID — это тихо
   сломанный звук, который никто не заметит до релиза.
4. Опубликовать место и проверить одну покупку с телефона.

Пункты 1–2 не блокируют работу: код пишется на нулях, лоты просто неактивны.

## Порядок работы

1. **Монетизация.** `Config/Monetization`, `PurchaseService`, `BoostService`,
   операции `DataService`, вкладка магазина, Studio-рычаг двойного чека.
   → закрывает первый критерий приёмки.
2. **Настройки, звук, мобильная вёрстка.** `UIScale`, режимы качества,
   `SoundController` на нулевых ID, панель настроек.
   → закрывает второй критерий в доступном объёме.
3. **Туториал.**
4. **Финал:** `Balance.Debug.showStats = false`, проход по всем панелям в
   эмуляции телефона, `stylua` + `selene` начисто, отчёт и инструкция проверки.

Этап режется на сессии по этим границам: после каждого шага код целостен и игра
играбельна (правило 9).

## Приёмка (раздел 9 ТЗ)

- Покупка обрабатывается ровно один раз даже при повторной отправке — проверяется
  Studio-рычагом на настоящем коде выдачи и одной реальной покупкой.
- На среднем Android игра стабильна весь забег — **закрывается частично**:
  проверяем вёрстку и тач-управление в эмуляции устройства Studio и
  производительность на ограниченном качестве. Настоящего замера на Android не
  будет, пока не появится устройство. Записано осознанно, не забыто.
